# Security & Code Audit Report — Unresolved Findings

**Project:** shawkath646-portfolio  
**Audit Date:** 2026-09-01 (Updated: 2026-09-04)  
**Framework:** Next.js 16.3.4 (App Router), React 19.2.8, TypeScript 6.0.3  

---

## Executive Summary

A comprehensive security, authentication, architecture, and code-quality audit of the Next.js portfolio repository was conducted. The project implements modern design patterns and several strong security practices (such as 12-round bcrypt hashing, TOTP two-factor authentication via `otplib`, HTTP-only SameSite=Strict cookies for admin web sessions, encrypted cookies via AES-GCM for shared files, HMAC-SHA256 hash-as-document-ID generic password storage, dynamic route scope enforcement with prefix/alias matching, and strict isolation between client-invocable `*.actions.ts` Server Actions and server-only `*.ts` modules).

Recent major refactorings have resolved all critical security and architectural concerns:
- **Server Actions Exposure Eliminated:** Non-client internal data fetchers (`getAdminData`, `getAllPersons`, `getPersonById`, `getPersonBySlug`, `getProjectsData`, `getSocialLinks`, `getLifeMilestones`, `sendNotificationToDevice`) were stripped of `"use server"`, converting them into pure server modules and eliminating publicly callable Next.js RPC endpoints.
- **Admin Data Authorization Hardened:** `getAdminAlbumsList` now requires active admin session validation (`getAuthSession()`), and `getAdminData()` is purely server-internal without public RPC exposure.
- **Generic Password Management Hardened:** Replaced plaintext passwords and hints with HMAC-SHA256 hash doc IDs, UUID generation, dynamic route scopes (`site_scopes.ts`), and high-performance compact route selection UI.
- **Person Detail Routes Hardened with Privacy-Preserving Search Indexing:** Direct access to `/[lang]/person/[slug]` now enforces `RestrictedPageLogin` and `isRouteAllowed` session validation. Search engines and unauthenticated visitors receive only the person's name and generic teaser description in metadata and page headers. All sensitive PII (DOB, meet/end dates, relationship timeline, and MDX narratives) are strictly gated behind password authentication.

The remaining unresolved vulnerabilities requiring remediation are detailed below:
1. **Proxy / JWT Desynchronization:** Stateless JWT verification in `proxy.ts` allows revoked/deleted sessions and generic user tokens to pass the admin proxy filter.
2. **Passwordless 2FA Deactivation:** `disable2FA()` can be executed without password or TOTP re-authentication.

## High Severity Findings

### [HIGH] Stateless JWT Verification in Proxy Permitting Access with Revoked/Deleted Sessions & Token Cross-Use

**Confidence:** CONFIRMED  
**Category:** Authentication & Session Management / Broken Access Control  
**Affected files:**  
- `src/proxy.ts`
- `src/actions/authentication/proxyHelperFunctions.ts`
- `src/actions/genericAuth/authSession.ts`
- `src/utils/tokens.ts`  
**Affected routes/functions:** `handleAdminRequest()`, `verifyToken()`, `createGenericAuthSession()`

**Problem**  
`handleAdminRequest` in the proxy verifies admin requests solely using `await verifyToken(accessToken)`. It does not verify whether the session exists in the Firestore `auth-sessions` collection. Moreover, `createGenericAuthSession` uses the exact same `AUTH_TOKEN_SECRET` and token payload structure (`{ sessionId }`) as admin sessions.

**Attack Scenario**  
1. When an admin logs out or an admin session is revoked from the dashboard, `verifyToken(accessToken)` still returns true because JWTs are valid for 7 days. The proxy permits the revoked token to pass through to `/admin`.
2. A generic user holding a `page_access_token` can set `access_token` and `refresh_token` cookies to their generic token value. `verifyToken` succeeds, granting entry past the proxy into `/admin`.

**Impact**  
Inability to revoke compromised tokens at the proxy boundary; cross-session type confusion between generic user and administrator tokens.

**Recommended Fix**  
1. Separate JWT signing keys or enforce distinct token payloads (e.g. `role: "admin"` vs `role: "generic"` with issuer/audience validation).
2. Ensure every admin page and Server Action enforces authoritative database session verification via `resolveSession()`.

**Priority:** High

---

### [HIGH] Passwordless 2FA Deactivation via `disable2FA` Without Re-Authentication

**Confidence:** CONFIRMED  
**Category:** Broken Authentication / Privilege Degradation  
**Affected files:**  
- `src/actions/authentication/manage2FA.actions.ts`  
**Affected routes/functions:** `disable2FA()`

**Problem**  
`disable2FA()` checks for an active session (`getAuthSession()`), but does not require the current admin password or a valid 2FA verification code before clearing `totpSecret`.

**Attack Scenario**  
An adversary with temporary physical access or an active admin session can immediately disable 2FA with a single action call, permanently degrading the account security posture.

**Impact**  
Unauthorized deactivation of multi-factor authentication.

**Recommended Fix**  
Require both the current admin password and a valid TOTP code as arguments to `disable2FA()` before clearing the secret:
```ts
export async function disable2FA(password: string, code: string): Promise<APIResponseType>
```

**Priority:** High

## Medium Severity Findings

### [MEDIUM] Unauthenticated Public File Upload with No MIME Validation and 500MB Size Limit

**Confidence:** CONFIRMED  
**Category:** File Upload Security / Abuse  
**Affected files:**  
- `src/actions/share/sharedFileManagement.actions.ts`  
**Affected routes/functions:** `requestSharedFileUploadURL()`, `saveSharedFile()`

**Problem**  
`requestSharedFileUploadURL` allows unauthenticated clients to request signed GCS upload URLs for files up to 500MB. There is no MIME type validation, file extension whitelist, CAPTCHA protection, or rate limiting on this endpoint.

**Attack Scenario**  
Malicious bots can spam the endpoint, uploading executable binaries or large files to exhaust GCS storage and generate excessive Firestore records.

**Impact**  
Storage resource exhaustion, financial cost inflation, hosting of arbitrary files.

**Recommended Fix**  
Apply strict file type whitelisting, reduce default file size limits, and require reCAPTCHA verification before generating upload URLs.

**Priority:** Medium

### [MEDIUM] Broken Authentication for Native / Desktop Clients (Tokens Not Returned)

**Confidence:** CONFIRMED  
**Category:** Authentication Architecture / Functional Defect  
**Affected files:**  
- `src/actions/authentication/auth.actions.ts`
- `src/app/api/client-app/verify-2fa/route.ts`  
**Affected routes/functions:** `verify2FA()`

**Problem**  
In `verify2FA()`, tokens are only written to cookies if `attempt.platform === "web"`. For `android` and `desktop` platforms, `verify2FA()` returns `{ success: true, message: "Verification successful" }` without returning the access or refresh token in the response body.

**Impact**  
Native desktop and Android client apps can never receive session tokens from `/api/client-app/verify-2fa` and are unable to authenticate against protected API routes.

**Recommended Fix**  
Return `tokens: { accessToken: session.accessToken, refreshToken: session.refreshToken }` in the response when `attempt.platform !== "web"`.

**Priority:** Medium

# Authentication & Authorization Deep Dive

## Admin Authentication

The admin authentication architecture uses a two-step flow:
1. **Step 1 (Password Verification):** `performLogin()` compares the plaintext password against the bcrypt hash in `site-config/admin-pass`. On match, a `login-attempts` record is created with status `"waiting"`.
2. **Step 2 (Two-Factor Authentication):** `verify2FA()` validates the 6-digit TOTP code against `adminPasswordRecord.totpSecret`. On success, an `auth-sessions` document is generated in Firestore, and two HTTP-only cookies (`access_token` valid for 7 days, `refresh_token` valid for 30 days) are set on the response.
3. **Proxy Verification:** `src/proxy.ts` calls `handleAdminRequest()`, which validates `access_token` via `verifyToken()`. If expired, it attempts a refresh using `refreshAuthSession()`.
4. **Session Resolution:** Server Actions call `getAuthSession()` -> `resolveSession()`, verifying document existence in Firestore.

**Unresolved Weaknesses:**
- 2FA can be disabled without re-entering password or OTP.
- The proxy performs stateless JWT verification, permitting revoked sessions to pass.

---

## General User Authentication

The general user authentication system (`genericAuth`) protects sensitive sections (`/about/personal-life`, `/about/love-corner`, `/about/friends-corner`, and person subroutes):
1. **Password Generation & Storage:** Generates random UUID passwords via `crypto.randomUUID()`. Computes HMAC-SHA256 hash using `AUTH_TOKEN_SECRET` as document ID. Raw passwords and hints are never stored in Firestore.
2. **Password Verification:** `handleGenericLogin()` verifies reCAPTCHA v3, computes the HMAC-SHA256 hash of the entered password, and executes an O(1) document lookup against `generic-passwords`.
3. **Route Authorization:** Verifies that `allowedRoutes` permits the target route via `isRouteAllowed()`, which enforces exact matches, parent prefix matches (`/about/love-corner` covering all children), and person alias matches (`/person/[slug]`).
4. **Session Creation:** `createGenericAuthSession()` writes a session record to `generic-sessions` granting `allowedRoutes` and issues a `page_access_token` cookie signed with `AUTH_TOKEN_SECRET`.
5. **Session Resolution:** `getGenericAuthSession(requestedRoute)` verifies that the session document exists in Firestore and that the requested route is unexpired and permitted via `isRouteAllowed()`.

**Unresolved Weaknesses:**
- Shared JWT secret between admin and generic auth enables token confusion.

## DRY / Refactoring Opportunities

1. **Token Generation & Verification Abstraction:**  
   `tokens.ts` handles generic JWT operations. Creating specialized wrappers (`createAdminToken`, `createGenericToken`) with distinct token types/secrets will eliminate cross-token confusion and code duplication between `authSession.ts` and `genericAuth/authSession.ts`.
2. **Revalidation Constants:**  
   Centralize route paths into a constants object to prevent route typos.
3. **Firestore Timestamp Mapping:**  
   `timestampToDate` conversions are duplicated across almost every action file. Implement standard Firestore converters (`FirestoreDataConverter`) for models (`PersonObject`, `GalleryImageType`, `AuthSessionRecord`).

## Performance & Optimization

### High Impact
- **Parallelize Person & Gallery Admin Queries:** In `src/app/admin/(dashboard)/security/page.tsx`, `Promise.all` is used properly; replicate this pattern in gallery and life admin pages where sequential waterfalls occur.

## Positive Security Practices

- **Strict Server Actions / Server-Only Architecture:** Enforced 100% boundary between `"use server"` files (`*.actions.ts`) and pure server modules (`*.ts`), eliminating accidental public RPC endpoint generation for internal queries.
- **Privacy-Preserving Search Indexing on Person Pages:** Public metadata and teaser views for `/[lang]/person/[slug]` expose only the person's name and generic narrative teaser to search engines, while completely concealing sensitive dates, contact info, and MDX stories behind route-scoped generic password authentication.
- **Strong Admin Password Hashing:** Uses `bcrypt` with 12 work factor salt rounds.
- **RFC 6238 TOTP Multi-Factor Authentication:** Proper two-step login flow with 2FA requirement.
- **Strict Cookie Flags for Web Admin:** `HttpOnly`, `SameSite=Strict`, `Secure` (in production), and bounded expiration.
- **End-to-End Encrypted Cookie for Upload Tracking:** `sfc` cookie uses `jose` AES-256-GCM authenticated encryption (`dir` algorithm).
- **Server/Client Isolation:** `getEnv.ts` uses `import "server-only";` to guard secrets from client bundling.
- **Signed GCS Upload URLs:** Direct-to-bucket uploads prevent large file payloads from passing through the Next.js server runtime.
- **JSON-LD Script Escaping:** `replace(/</g, "\\u003c")` correctly sanitizes structured data script tags.
- **Authoritative Cloudflare Real IP Detection:** Prioritizes `cf-connecting-ip` and `true-client-ip` to prevent header spoofing against rate limits and blocklists.
- **SSRF Protection in MDX Renderer:** Whitelists approved GCS bucket domains and paths before fetching remote content.
- **Admin Password Reset Session Purge:** Invalidation of all existing active sessions upon password changes.
- **HMAC-SHA256 Generic Password Hashing:** Uses HMAC-SHA256 with server secret as document ID; raw passwords and hints are never stored in Firestore.
- **Route-Scoped Access Control:** Dynamic `site_scopes.ts` defines granular permissions per key; Next.js `unauthorized()` is triggered upon unauthorized route traversal.

## Recommended Remediation Order

### Phase 1 — Immediate (Critical Security Fixes)
- *All critical security vulnerabilities have been remediated.*

### Phase 2 — High Priority (Authentication & Boundary Hardening)
1. **Secure 2FA Deactivation:** Require password and OTP confirmation in `disable2FA()`.
2. **Separate Token Secrets:** Use distinct signing keys or claims for admin vs generic access tokens to eliminate proxy bypass and cross-role confusion.

### Phase 3 — Hardening (Defense-in-Depth & File Security)
1. **Configure Global Security Headers:** Add HSTS, X-Content-Type-Options, X-Frame-Options, and Referrer-Policy in `next.config.ts`.
2. **Validate Shared File Uploads:** Restrict MIME types, reduce size limits, and add reCAPTCHA to `requestSharedFileUploadURL`.
3. **Exclude Private Routes from Sitemap:** Remove `/about/personal-life`, `/about/love-corner`, and `/about/friends-corner` from `sitemap.ts` and add to `robots.ts`.

### Phase 4 — Performance & Functional Refinement
1. **Implement Contact Form Backend:** Connect `ContactForm.tsx` to a real storage/email action.
2. **Fix Client-App 2FA Response:** Return tokens to Android/desktop platforms in `verify2FA()`.
3. **Delete Unused Notification File:** Remove `sendNotificationToDevice.ts`.
4. **Optimize Gallery Images:** Add `sizes` and lazy loading to image grids.

## Final Assessment

### Summary:
- **Biggest Current Weaknesses:** Stateless proxy JWT verification and passwordless 2FA deactivation.
- **Highest-Priority Fix:** Require password and OTP verification on `disable2FA()`, and separate JWT signing keys between admin and generic auth.
- **Authentication Assessment:** Admin authentication has been hardened (Cloudflare real-IP resolution, server-only credentials data access, session revocation on password change, and strict Server Actions boundaries), but remains vulnerable to stateless proxy bypass and passwordless 2FA disabling. Generic user authentication has been upgraded to cryptographically secure HMAC-SHA256 hash-as-document-ID architecture with route-scoped authorization.
- **Authorization Assessment:** Fully hardened across both Server Actions and page routes. Internal data queries have had `"use server"` removed to prevent RPC abuse, and individual person pages (`/[lang]/person/[slug]`) enforce route-level password verification while maintaining clean, privacy-preserving metadata for search engine indexing.
- **Code Quality Assessment:** Clean TypeScript architecture, strict `*.actions.ts` naming convention, well-organized component hierarchy, and complete dead-file purge across legacy action files.
- **Performance Assessment:** Strong baseline with React 19 compiler and Next.js 16 App Router, with sub-millisecond dynamic scope evaluation in `site_scopes.ts`.
