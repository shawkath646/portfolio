# Security & Code Audit Report

**Project:** shawkath646-portfolio  
**Audit Date:** 2026-09-01  
**Framework:** Next.js 16.3.2 (App Router), React 19.2.8, TypeScript 6.0.3  
**Overall Risk:** Critical  

---

## Executive Summary

A comprehensive security, authentication, architecture, and code-quality audit of the entire Next.js portfolio repository was conducted. The project implements modern design patterns and several strong security practices (such as 12-round bcrypt hashing, TOTP two-factor authentication via `otplib`, HTTP-only SameSite=Strict cookies for admin web sessions, encrypted cookies via AES-GCM for shared files, and isolated `server-only` environment utilities).

However, critical vulnerabilities exist that undermine the security perimeter:
1. **IP Header Spoofing [RESOLVED]:** Rate limiting and IP blocklists in `getClientIP` previously evaluated spoofable client-controlled headers first. This has been remediated by prioritizing authoritative Cloudflare proxy headers (`CF-Connecting-IP`, `True-Client-IP`) before falling back to other headers.
2. **Critical Secret Exposure [RESOLVED]:** Previously, `getAdminCredentials` was an exported Server Action (`"use server"`), exposing a public HTTP RPC endpoint returning the admin bcrypt password hash and TOTP secret. The `"use server"` directive was removed, transforming it into an internal server-only data-fetching utility for Server Components, with the password hash stripped from memory.
3. **Plaintext Password Storage:** The general user authentication system (`genericAuth`) stores all restricted-page access passwords in plaintext in Firestore and exposes them via `getAllPasswords`.
4. **Broken Access Control on PII:** The `getAllPersons`, `getPersonById`, and `getPersonBySlug` Server Actions and the `/[lang]/person/[slug]` route have no authentication checks, exposing sensitive personal data (phone numbers, physical addresses, emails, DOB, and relationship histories) despite restricted-page UI locks.
5. **Proxy / JWT Desynchronization:** Stateless JWT verification in `proxy.ts` allows revoked/deleted sessions and generic user tokens to pass the admin proxy filter.

Remediation must prioritize hashing generic passwords and enforcing server-side authorization on all personal data queries.

## Critical Findings

### [CRITICAL - RESOLVED] Client IP Header Spoofing Enables Complete Admin Rate-Limit & IP Blocklist Bypass

**Status:** RESOLVED (Remediated on 2026-09-01)  
**Resolution:** Refactored `src/utils/ipAddress.ts` (`getClientIP`) to strictly prioritize authoritative Cloudflare proxy headers (`CF-Connecting-IP`, `True-Client-IP`) before inspecting fallback headers (`X-Real-IP`, `X-Forwarded-For`, etc.). When deployed behind Cloudflare proxy, client-supplied spoofing headers cannot override the connecting IP address.  
**Confidence:** CONFIRMED  
**Category:** Authentication / Rate Limiting / Access Control Bypass  
**Affected files:**  
- `src/utils/ipAddress.ts`
- `src/actions/authentication/authActions.ts`
- `src/actions/authentication/loginRateLimit.ts`  
**Affected routes/functions:** `getClientIP()`, `performLogin()`, `isLoginAllowed()`

**Problem**  
`getClientIP` (in `src/utils/ipAddress.ts`) previously iterated over a flat list of client-supplied HTTP request headers starting with `x-client-ip` and accepted the first valid public IP address found. Because incoming request headers could be arbitrarily set by an attacker, an adversary could spoof any IP address.

**Attack Scenario**  
An attacker launches a brute-force or credential-stuffing attack against `/admin/login` or `performLogin()`. On each attempt, the attacker supplies a randomly generated IP header (e.g. `X-Client-IP: 198.51.100.X` or `X-Forwarded-For: 203.0.113.X`). Because `isLoginAllowed` queries Firestore for failed attempts filtered by `ipAddress`, the rate-limit threshold (3 failed attempts per hour) is never reached. Furthermore, if an IP is placed on `adminPasswordRecord.blockedIPs`, changing the header immediately circumvents the block.

**Impact**  
Complete nullification of brute-force protection and IP-based access controls on the administrative authentication interface.

**Remediation Applied**  
Prioritized authoritative Cloudflare edge headers (`cf-connecting-ip`, `true-client-ip`) in `getClientIP()`. Fallback headers (`x-real-ip`, `x-forwarded-for`, etc.) are now only queried if Cloudflare headers are absent, with full validation on IP formatting and private IP ranges.

**Priority:** Immediate (Addressed)

### [CRITICAL - RESOLVED] Admin Password Hash and Raw TOTP Secret Exposure via `getAdminCredentials` Server Action

**Status:** RESOLVED (Remediated on 2026-09-01)  
**Resolution:** Removed the `"use server"` directive from `src/actions/admin/getAdminCredentials.ts`. Next.js no longer generates a public HTTP POST RPC endpoint for this function. It now executes strictly as an internal server utility during Server Component rendering (`src/app/admin/(dashboard)/security/page.tsx`), and `data.password` is explicitly cleared in memory.  
**Confidence:** CONFIRMED  
**Category:** Sensitive Data Exposure / Privilege Escalation  
**Affected files:**  
- `src/actions/admin/getAdminCredentials.ts`
- `src/app/admin/(dashboard)/security/page.tsx`  
**Affected routes/functions:** `getAdminCredentials()`

**Problem**  
`getAdminCredentials` was previously an exported `"use server"` Server Action that retrieved the entire Firestore document `site-config/admin-pass` and returned it directly over a public HTTP RPC endpoint. The returned object contained `password` (the bcrypt password hash) and `totpSecret` (the unencrypted base32 TOTP secret).

**Attack Scenario**  
Any client with an active session (or executing in an admin context via XSS or browser automation) could invoke `getAdminCredentials()` via HTTP POST with `Next-Action`. The response payload delivered the raw `totpSecret` and `password` hash over the wire. The attacker could permanently import the TOTP secret into an authenticator application to generate valid 2FA codes offline, and crack the bcrypt hash offline.

**Impact**  
Permanent compromise of multi-factor authentication (2FA) and extraction of the administrator's password hash.

**Remediation Applied**  
Removed the `"use server"` directive from `src/actions/admin/getAdminCredentials.ts`, eliminating the public HTTP endpoint completely. The function now runs exclusively within the Node.js server context when rendering the `Page` Server Component, and `password` is set to `""`.

**Priority:** Immediate (Addressed)

### [CRITICAL] Plaintext Storage and Direct Exposure of Generic User Passwords

**Confidence:** CONFIRMED  
**Category:** Insecure Cryptographic Storage / Information Disclosure  
**Affected files:**  
- `src/actions/genericAuth/passwordManagement.ts`
- `src/actions/genericAuth/authActions.ts`  
**Affected routes/functions:** `generatePassword()`, `getAllPasswords()`, `handleGenericLogin()`

**Problem**  
The password management subsystem stores passwords for protected pages (`personal_life`, `friends_corner`, `love_corner`) in plaintext in the Firestore `generic-passwords` collection. In `handleGenericLogin`, passwords are queried with `.where("password", "==", password)`. Furthermore, `getAllPasswords()` fetches and transmits the entire `password` field in plaintext to the admin dashboard.

**Attack Scenario**  
Anyone with read access to Firestore, database backups, or any client inspecting the Server Action network payload of `getAllPasswords()` receives all generated passwords in plaintext.

**Impact**  
Complete compromise of all generic access passwords; violation of basic cryptographic storage standards.

**Recommended Fix**  
1. Hash passwords using `bcrypt` before storing in `generic-passwords` (store `passwordHash` instead of `password`).
2. Replace direct Firestore equality queries with document lookup and `await bcrypt.compare(inputPassword, record.passwordHash)`.
3. In `getAllPasswords()`, exclude the password field and return only non-sensitive metadata (`passwordHint`, `accessScope`, `usableTimes`, `usedTimes`, `expiresAt`, `createdAt`).

**Priority:** Immediate

### [CRITICAL] Broken Access Control on Personal Data Server Actions Exposing Sensitive PII

**Confidence:** CONFIRMED  
**Category:** Broken Access Control / Information Disclosure / IDOR  
**Affected files:**  
- `src/actions/person/getPersonData.ts`
- `src/app/[lang]/person/[slug]/page.tsx`  
**Affected routes/functions:** `getAllPersons()`, `getPersonById()`, `getPersonBySlug()`, `PersonPage`

**Problem**  
The application uses `RestrictedPageLogin` on `/about/friends-corner` and `/about/love-corner` to lock pages behind generic passwords. However, the backing Server Actions `getAllPersons()`, `getPersonById`, and `getPersonBySlug()` have NO session verification or authorization checks. In addition, the route `/[lang]/person/[slug]` is public and performs no authentication check before rendering person data.

**Attack Scenario**  
An unauthenticated user can invoke `getAllPersons("love corner")` or `getAllPersons("friends")` directly via Server Action RPC from their browser console or `curl`, or navigate directly to `/[lang]/person/<slug>`. The returned `PersonObject` records contain sensitive PII including phone numbers (`phone`), physical addresses (`address`), email addresses (`email`), dates of birth (`dob`), and private relationship timelines.

**Impact**  
Total exposure of sensitive personal information for all friends and love corner entries without entering any password.

**Recommended Fix**  
1. Enforce authorization checks inside `getAllPersons`, `getPersonById`, and `getPersonBySlug` verifying either an active admin session or a valid `generic-sessions` record matching the required `accessScope`.
2. Strip private fields (`phone`, `address`, `email`, `dob`) from public representations.
3. Protect `/[lang]/person/[slug]` with `getAuthSession()` / `getGenericAuthSession()` checks matching the person's category.

**Priority:** Immediate

## High Severity Findings

### [HIGH] Stateless JWT Verification in Proxy Permitting Access with Revoked/Deleted Sessions & Token Cross-Use

**Confidence:** CONFIRMED  
**Category:** Authentication & Session Management / Broken Access Control  
**Affected files:**  
- `src/proxy.ts`
- `src/actions/authentication/proxyHelperFunctions.ts`
- `src/actions/genericAuth/authSession.ts`
- `src/utils/tokens.ts`  
**Affected routes/functions:** `handleAdminRequest()`, `verifyToken()`, `createGenericAuthSession()`

**Problem**  
`handleAdminRequest` in the proxy verifies admin requests solely using `await verifyToken(accessToken)`. It does not verify whether the session exists in the Firestore `auth-sessions` collection. Moreover, `createGenericAuthSession` uses the exact same `AUTH_TOKEN_SECRET` and token payload structure (`{ sessionId }`) as admin sessions.

**Attack Scenario**  
1. When an admin logs out or an admin session is revoked from the dashboard, `verifyToken(accessToken)` still returns true because JWTs are valid for 7 days. The proxy permits the revoked token to pass through to `/admin`.
2. A generic user holding a `page_access_token` can set `access_token` and `refresh_token` cookies to their generic token value. `verifyToken` succeeds, granting entry past the proxy into `/admin`.

**Impact**  
Inability to revoke compromised tokens at the proxy boundary; cross-session type confusion between generic user and administrator tokens.

**Recommended Fix**  
1. Separate JWT signing keys or enforce distinct token payloads (e.g. `role: "admin"` vs `role: "generic"` with issuer/audience validation).
2. Ensure every admin page and Server Action enforces authoritative database session verification via `resolveSession()`.

**Priority:** High

**Category:** Broken Access Control / Abuse / Spam

```ts
const adminSession = await getAuthSession();

```

### [HIGH - RESOLVED] Server-Side Request Forgery (SSRF) in `MDXRenderer` via Unvalidated `mdxUrl`

**Status:** RESOLVED (Remediated on 2026-09-01)  
**Resolution:** Added `isValidMdxUrl` validation to `src/components/MDXRenderer.tsx` requiring HTTPS and whitelisting trusted Google Cloud / Firebase Storage bucket hosts matching `persons-mdx/`. Added URL and file type validation to `src/actions/person/personManagement.ts` (`requestMdxUploadURL` and `savePersonAction`).  
**Confidence:** CONFIRMED  
**Category:** Server-Side Request Forgery (SSRF)  
**Affected files:**  
- `src/components/MDXRenderer.tsx`
- `src/actions/person/personManagement.ts`  
**Affected routes/functions:** `MDXRenderer()`, `savePersonAction()`, `requestMdxUploadURL()`

**Problem**  
In `src/components/MDXRenderer.tsx`, the server component previously executed `await fetch(mdxSource)` during server-side rendering without validating the host or scheme.

**Attack Scenario**  
If an attacker supplied an internal address (e.g. `http://169.254.169.254/latest/meta-data/` or internal LAN endpoints) as the `mdxUrl` of a person record, the Next.js server would make an outbound HTTP request to the internal resource upon rendering the person page.

**Impact**  
Cloud metadata enumeration, internal network scanning, SSRF.

**Remediation Applied**  
Strict domain, scheme, and path validation in `MDXRenderer.tsx` blocks any non-bucket URLs from being fetched. MIME validation was added to `requestMdxUploadURL` and URL pattern verification was added to `savePersonAction`.

**Priority:** High (Addressed)

### [HIGH - RESOLVED] Password Change Does Not Invalidate Active Sessions

**Status:** RESOLVED (Remediated on 2026-09-01)  
**Resolution:** Updated `src/actions/authentication/changeAdminPassword.ts` to batch-delete all active session documents from the `auth-sessions` collection upon password change and delete current session cookies (`access_token`, `refresh_token`), forcing all devices to re-authenticate with the new password.  
**Confidence:** CONFIRMED  
**Category:** Session Management / Incomplete Revocation  
**Affected files:**  
- `src/actions/authentication/changeAdminPassword.ts`  
**Affected routes/functions:** `changeAdminPassword()`

**Problem**  
When the administrator changed their password via `changeAdminPassword()`, the record in `site-config/admin-pass` was updated, but active sessions in the `auth-sessions` collection were previously left intact.

**Attack Scenario**  
If an administrator changed credentials following a suspected session hijacking or credential compromise, the attacker's existing JWTs and refresh tokens would remain active for up to 30 days.

**Impact**  
Persistent unauthorized access following a password reset.

**Remediation Applied**  
All active sessions in `auth-sessions` are now automatically purged on password update, and session cookies are cleared.

**Priority:** High (Addressed)

### [HIGH - RESOLVED] Open Redirect Vulnerability on Admin Login Page

**Status:** RESOLVED (Remediated on 2026-09-01)  
**Resolution:** Updated `src/app/admin/(auth)/login/LoginPageContainer.tsx` to validate `redirect` search parameter, ensuring it is strictly a relative path beginning with `/` and not containing protocol-relative `//` or backslash bypasses.  
**Confidence:** CONFIRMED  
**Category:** Open Redirect  
**Affected files:**  
- `src/app/admin/(auth)/login/LoginPageContainer.tsx`  
**Affected routes/functions:** `LoginPageContainer()`

**Problem**  
In `LoginPageContainer.tsx`, the redirect destination after successful 2FA login was previously retrieved directly from `searchParams.get('redirect')` and passed to `router.replace(redirectUrl)` without origin or relative path validation.

**Attack Scenario**  
An attacker could craft a link `https://<domain>/admin/login?redirect=https://attacker.com/fake-admin` to redirect the administrator to an external malicious domain immediately after authentication.

**Impact**  
Phishing and post-authentication token/credential harvesting.

**Remediation Applied**  
Sanitized `redirectUrl` to enforce relative paths only (`startsWith('/') && !startsWith('//') && !includes('\\')`), falling back to `/admin`.

**Priority:** High (Addressed)

# Authentication & Authorization Deep Dive

## Admin Authentication

The admin authentication architecture uses a two-step flow:
1. **Step 1 (Password Verification):** `performLogin()` compares the plaintext password against the bcrypt hash in `site-config/admin-pass`. On match, a `login-attempts` record is created with status `"waiting"`.
2. **Step 2 (Two-Factor Authentication):** `verify2FA()` validates the 6-digit TOTP code against `adminPasswordRecord.totpSecret`. On success, an `auth-sessions` document is generated in Firestore, and two HTTP-only cookies (`access_token` valid for 7 days, `refresh_token` valid for 30 days) are set on the response.
3. **Proxy Verification:** `src/proxy.ts` calls `handleAdminRequest()`, which validates `access_token` via `verifyToken()`. If expired, it attempts a refresh using `refreshAuthSession()`.
4. **Session Resolution:** Server Actions call `getAuthSession()` -> `resolveSession()`, verifying document existence in Firestore.

**Weaknesses Identified:**
- Rate limiting and IP blocking previously relied on spoofable headers; now remediated by prioritizing Cloudflare proxy headers (`CF-Connecting-IP`, `True-Client-IP`).
- `getAdminCredentials` leaks the raw password hash and TOTP secret.
- Changing admin password does not invalidate existing sessions.
- 2FA can be disabled without re-entering password or OTP.
- The proxy performs stateless JWT verification, permitting revoked sessions to pass.

**Admin Authentication Rating:** Medium Risk (reduced from High following Cloudflare real-IP header enforcement; remaining risk from credential leaks and proxy session desynchronization).

---

## General User Authentication

The general user authentication system (`genericAuth`) protects sensitive sections (`/about/personal-life`, `/about/love-corner`, `/about/friends-corner`):
1. **Password Verification:** `handleGenericLogin()` verifies reCAPTCHA v3 and queries `generic-passwords` matching `password` and `accessScope`.
2. **Session Creation:** `createGenericAuthSession()` writes a session record to `generic-sessions` and issues a `page_access_token` cookie signed with `AUTH_TOKEN_SECRET`.
3. **Session Resolution:** `getGenericAuthSession(scope)` verifies that the session document exists in Firestore and that the requested scope is unexpired.

**Weaknesses Identified:**
- Passwords are stored and queried in **plaintext** in Firestore.
- Underlying Server Actions (`getAllPersons`, `getPersonById`, `getPersonBySlug`) have **zero authorization checks**, completely bypassing the password wall.
- Typo in `clearGenericAuthSession` (`"geneic-sessions"`) breaks logout document deletion.
- Shared JWT secret between admin and generic auth enables token confusion.

**General Authentication Rating:** Critical Risk (due to plaintext storage and completely missing authorization on backing Server Actions).

# Positive Security Practices

- **Strong Admin Password Hashing:** Uses `bcrypt` with 12 work factor salt rounds.
- **RFC 6238 TOTP Multi-Factor Authentication:** Proper two-step login flow with 2FA requirement.
- **Strict Cookie Flags for Web Admin:** `HttpOnly`, `SameSite=Strict`, `Secure` (in production), and bounded expiration.
- **End-to-End Encrypted Cookie for Upload Tracking:** `sfc` cookie uses `jose` AES-256-GCM authenticated encryption (`dir` algorithm).
- **Server/Client Isolation:** `getEnv.ts` uses `import "server-only";` to guard secrets from client bundling.
- **Signed GCS Upload URLs:** Direct-to-bucket uploads prevent large file payloads from passing through the Next.js server runtime.
- **JSON-LD Script Escaping:** `replace(/</g, "\\u003c")` correctly sanitizes structured data script tags.

# Final Assessment

## Overall Security Rating
**Critical Risk**

### Summary:
- **Biggest Current Weakness:** Broken authorization and plaintext storage in generic user authentication.
- **Strongest Existing Security Control:** Robust two-factor TOTP implementation with 12-round bcrypt password hashing, HTTP-only SameSite=Strict cookie architecture, and Cloudflare-prioritized real IP resolution.
- **Highest-Priority Fix:** Hash generic passwords and enforce server-side access control on all person PII queries (IP spoofing and getAdminCredentials exposure resolved).
- **Authentication Assessment:** Admin authentication architecture is well-designed in principle with Cloudflare real-IP resolution and server-only credentials fetching now active, but remains vulnerable to stateless proxy bypass. Generic user authentication requires complete cryptographic refactoring.
- **Authorization Assessment:** Severely inconsistent between client UI (which displays password gates) and backing Server Actions (which lack server-side permission checks).
- **Code Quality Assessment:** Clean TypeScript architecture and well-organized component hierarchy, but impacted by abandoned feature files (`LoginWithDevices`, `googleDrive`), typos (`geneic-sessions`, `/admin/secure`), and unused dependencies.
- **Performance Assessment:** Good foundation with React 19 compiler and Next.js 16 App Router caching, with significant optimization opportunities available by eliminating `googleapis` and caching MDX compilation.
